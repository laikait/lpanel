# LPA ↔ LPanel protocol, version 1

Status: **Draft, implemented through M4** (enrollment, heartbeat, rotation, revocation in M3; claim, lease, result and cancellation in M4). Changes to it require an ADR.
Decisions this rests on: [ADR-0001](adr/0001-lpa-in-go.md),
[ADR-0002](adr/0002-agent-pull-transport.md),
[ADR-0006](adr/0006-operations-separate-from-queue.md),
[ADR-0009](adr/0009-lpa-privilege-split.md).

The agent opens every connection. The panel never contacts a managed server.

## 1. Keys and identities

| Key | Algorithm | Generated by | Stored | Used for |
|---|---|---|---|---|
| Agent signing key | Ed25519 | LPA at enrollment | `/etc/lpa/agent.key`, `0600 lpa:lpa` | signs every agent request |
| Agent TLS client cert | ECDSA P-256, self-signed, 1 year | LPA at enrollment | `/etc/lpa/tls.{crt,key}`, `0600 lpa:lpa` | mTLS to panel Nginx |
| Panel operation-signing key | Ed25519 | LPanel installer | `/etc/lpanel/keys/operations.key`, `0640 root:lpanel`. **Not in the DB** | signs every operation sent to agents |
| Panel TLS cert | whatever panel Nginx serves | admin / installer | panel Nginx | agent pins its SPKI SHA-256 |

- Agent identity is a UUIDv4 `agent_id`, assigned by the panel at enrollment.
- Stored panel-side per agent: `agent_id`, the agent's Ed25519 public key, its TLS cert SHA-256 fingerprint, and the key state (`active` / `rotating` / `revoked`).
- Key ids (`kid`) are the first 16 characters of `base64url(sha256(public_key))`.
- **Encoding everywhere:** "base64url" means RFC 4648 §5 **without padding**. Hex is lower case. Times are integer unix seconds.
- The TLS client-cert fingerprint is `sha256` (hex) over the certificate's DER bytes.

## 2. Transport

- HTTPS to `https://<panel-host>:8444/agent/v1/...`, a listener for agents only ([ADR-0012](adr/0012-panel-package-php-fpm-and-agent-port.md)); people use 8443, where `/agent/` is 404. TLS 1.2 is the minimum and 1.3 is preferred.
- The agent pins the SPKI fingerprint of the agent listener's key (`/etc/lpanel/tls/agent.key`), which is never replaced. The browser certificate on 8443 can be, without affecting agents.
- Panel Nginx does `ssl_verify_client optional_no_ca` on the agent listener, and passes `$ssl_client_escaped_cert` and `$ssl_client_verify` as FastCGI params. It does **not** pass `$ssl_client_fingerprint`, which is SHA-1. LPanel decodes the PEM, computes the SHA-256 DER fingerprint, and rejects any `/agent/v1/*` request whose fingerprint doesn't match the agent named in its signature. Enrollment is the exception: there the fingerprint is recorded, not checked.
- These routes are a group with `'csrf' => false` and `'rate_limit'` per agent. The session cookie is never read, because a route with `csrf` off authenticates nothing by cookie (`docs/reference/security.md:61-66`).
- Request bodies are capped at 1 MiB. Result payloads above 256 KiB are refused, so an agent truncates and flags the result instead.

## 3. Signed agent requests

Every request after enrollment carries these headers:

```
LPA-Agent: <agent_id>
LPA-Key: <kid>
LPA-Request-Id: <UUIDv4>
LPA-Issued-At: <unix seconds>
LPA-Expires-At: <unix seconds>         # issued_at < expires_at <= issued_at + 120
LPA-Content-SHA256: <hex sha256 of the raw body bytes>
LPA-Signature: <base64url Ed25519 signature>
```

The signature is over this exact byte string: UTF-8, fields joined by `\n`, no trailing newline.

```
LPA-v1
<HTTP method, upper case>
<request path, no query string>
<agent_id>
<kid>
<request_id>
<issued_at>
<expires_at>
<content sha256 hex>
```

**Panel checks, in this order** (each failure has its own error code, §8):

1. Headers are present and well-formed. The agent exists and is not revoked. `kid` is one of its active keys.
2. The mTLS client-cert fingerprint matches the agent.
3. `|now − issued_at| ≤ 60s` and `now < expires_at`.
4. `sha256(body)` equals `LPA-Content-SHA256`.
5. The signature verifies.
6. `request_id` hasn't been seen for this agent. Seen ids are stored until `expires_at + 60s`, which is the replay window.
7. Rate limit per agent.

The body is never parsed before step 5.

## 4. Endpoints

All are `POST`, with JSON bodies, answering in LPHP's error shape (`{"error":{...}}`) on failure. The panel adds the protocol's error code as `error.code` (an extra key, which LPHP's `ErrorDocument` allows), so the agent can tell `replayed_request` from `bad_signature` without parsing messages. Responses are decoded leniently, so a newer panel may add fields; operations are decoded strictly.

| Path | Purpose | Body → Response |
|---|---|---|
| `/agent/v1/enroll` | one-time pairing (§5) | `{token, agent_public_key, tls_cert_sha256, facts}` → `{agent_id, panel_operation_key, poll}` |
| `/agent/v1/heartbeat` | liveness, version, capability document | `{agent_version, protocols:[1], capabilities:{op:[versions]}, health}` → `{server_time, poll, rotate_requested}` |
| `/agent/v1/operations/claim` | take up to `max` queued operations | `{max:1}` → `{operations:[SignedOperation]}` (empty if none) |
| `/agent/v1/operations/{id}/lease` | extend the lease while running | `{attempt}` → `{lease_until, cancel_requested}` |
| `/agent/v1/operations/{id}/result` | final result | Result (§7) → `{accepted:true}` |

An agent only ever learns of its own server's operations: a lease or result for any other id is `404 operation_not_found`.
| `/agent/v1/keys/rotate` | register a new agent key (signed by the **old** key) | `{new_public_key, new_tls_cert_sha256}` → `{kid}` |

Poll timing: when idle, poll every `poll.idle` seconds (5) ± 20% jitter. After a claim, poll again at once. On panel errors, back off exponentially to `poll.max` (300s).

## 5. Enrollment

1. An administrator creates an enrollment in LPanel for a server record. The panel:
   - generates a 32-byte random token;
   - stores only `sha256(token)`, with a 15-minute expiry, the creator and `single_use`;
   - shows the token once, together with the panel's SPKI fingerprint and a ready-made command:
     `lpa enroll --panel https://panel.example:8444 --pin sha256/<spki> --token <token>`
2. On the server (as root), `lpa enroll`:
   - generates the agent key and TLS cert;
   - connects with the pin;
   - posts `/agent/v1/enroll` with the token, its public key, its cert fingerprint and `facts` (OS release, kernel, hostname, machine-id hash, agent version).
   - signs the request like any other (§3) with the **new** agent key and `LPA-Agent: enroll`, which proves it holds the key it is registering. The panel verifies against `agent_public_key` from the body, then checks that the mTLS fingerprint equals `tls_cert_sha256`.
3. The panel checks the token in constant time against the stored hash. It must not be expired, consumed or revoked. The panel also rate-limits enrollment per IP to 10 per hour. Then, in one transaction, it:
   - marks the token consumed;
   - stores the agent's credentials;
   - binds the server record to `agent_id`;
   - writes an audit event.
4. The response carries `agent_id` and the panel's operation-signing **public** key. LPA stores both under `/etc/lpa/`.
5. A token that is wrong, expired or reused gets the same error to the caller (`enrollment_invalid`). The audit log records the precise reason.

**Revocation** marks the agent's credentials revoked. Every later request fails at check 1, and queued operations for that server become `cancelled`. Re-adding the server needs a new enrollment.

**Rotation** (built in M3). The panel sets `rotate_requested` in the heartbeat answer, or the agent rotates by itself once its identity is 90 days old.

1. The agent makes a new signing key and TLS certificate. It saves them under its state directory, `/var/lib/lpa/keys/<kid>/`, and writes that kid to `keys/pending`.
   - `/etc/lpa` stays read-only to the running agent, because it holds the trust anchors (the panel pin and the panel operation key).
2. It posts `/agent/v1/keys/rotate`, signed and sent over mTLS with the **current** key and certificate:
   - body: `{"new_public_key": "<b64url>", "new_tls_cert_sha256": "<hex>", "proof": "<b64url>"}`;
   - `proof` is the **new** key's Ed25519 signature over `LPA-ROTATE-v1\n<agent_id>\n<new kid>\n<new_tls_cert_sha256>`, which shows the agent holds the key it registers.
3. The panel accepts it only from the agent's `active` key. A key in its overlap gets `409`.
   - The new kid must be unused and the proof must verify (`bad_signature` otherwise).
   - In one transaction the old key becomes `rotating` with `retire_at` = now + 24 h, the new key becomes `active`, and `rotate_requested` is cleared.
   - Answer: `{"kid": "<new kid>"}`.
4. The agent writes the new kid to `keys/current` (one atomic write) and switches clients. From then on it loads `keys/current` in preference to `/etc/lpa`.
5. During the overlap the panel accepts both keys, each only with its own certificate. `servers:sweep` (every minute) revokes the old key at `retire_at`.

**If the answer is lost**, a `pending` file stays behind. At the next heartbeat (and at start-up) the agent asks the panel with the pending identity itself:
- accepted: it becomes `current`;
- refused with a 4xx: it is discarded;
- no answer: it is kept, and the agent asks again later.

It never starts a second rotation while one is pending, since that could orphan a key the panel has already taken. `lpa enroll` removes `/var/lib/lpa/keys`, so a new enrollment is never overridden by an older rotated key.

## 6. Operations

### 6.1 Signed operation (panel → agent)

```json
{
  "operation": "<base64url of the operation JSON bytes>",
  "kid": "<panel key id>",
  "signature": "<base64url Ed25519 over the raw operation bytes, prefixed by 'LPA-OP-v1\n'>"
}
```

The agent verifies the signature over the **exact decoded bytes** before parsing them. This avoids having to canonicalize JSON.

An operation whose signature fails is **not answered with a result**. Its
contents are untrusted, so the agent won't sign a statement about them. It logs
`bad_signature`, reports it in the next heartbeat's `health.last_errors`, and
lets the lease lapse. The decoded operation:

```json
{
  "v": 1,
  "operation_id": "UUIDv4",
  "agent_id": "UUIDv4",
  "op": "system.info",
  "op_version": 1,
  "target": { "server_id": "…" },
  "idempotency_key": "UUIDv4 or null for read-only",
  "attempt": 1,
  "issued_at": 1793000000,
  "not_after": 1793000600,
  "lease_seconds": 120,
  "timeout_seconds": 60,
  "payload": { }
}
```

**The agent refuses**, and sends a `failed` result with the matching code, when:

- `agent_id` isn't its own;
- `not_after` has passed;
- `op` or `op_version` isn't in its compiled-in registry;
- the payload doesn't validate against that operation's schema (unknown fields are an error, not ignored);
- the `operation_id` + `attempt` pair was already received. **Exception:** this one gets no new result. A fresh `failed` would overwrite the panel's record of the first run, so the agent resends the first run's result if it is still in its outbox, and otherwise only records `duplicate_delivery` for its next heartbeat.

### 6.2 Operation definitions

Every operation exists twice, with the same contract: in LPA's registry (Go) and in LPanel's Operations catalogue (PHP). Each declares:

| Field | Meaning |
|---|---|
| `op`, `op_version` | stable id, e.g. `website.create` v1 |
| `mutating` | false = read-only |
| `idempotent` | safe to re-run with the same `idempotency_key` |
| `capability` | the LPanel capability needed to request it (e.g. `servers.read`) |
| `scope` | `server`, `account`, `website`, … — what `target` must name |
| `payload_schema`, `result_schema` | strict JSON schemas; `additionalProperties: false` |
| `timeout_seconds`, `max_output_bytes` | upper bounds; the agent enforces them |
| `max_attempts` | for idempotent ops only |
| `audit` | `info` / `notice` / `critical` |
| `pre`, `post` | preconditions checked before acting, postconditions verified after |
| `compensation` | the rollback step, or `none` with a documented recovery |

**Read-only operations (idempotent, server scope; the agent runs them itself):**

| op | Result (summary) |
|---|---|
| `agent.health` | uptime, journal size, last error codes |
| `agent.capabilities` | `{op: [versions]}`, protocol versions, build info |
| `system.info` | OS id/version (from `/etc/os-release`), kernel, hostname, CPU count, memory total, architecture |
| `system.metrics` | load 1/5/15, memory used/available, swap, per-mount disk and inode usage (allowlisted mount types) |
| `service.list_status` | state of an **allowlisted** set of units (`nginx`, `apache2`, `php*-fpm`, `mariadb`, `lpanel-nginx`, `lpa-agent`); **no** arbitrary unit names |

**Account operations (M6a, [ADR-0013](adr/0013-hosting-accounts-on-a-server.md); mutating, idempotent, account scope; only `lpa-exec` runs them):**

| op | Payload | Result |
|---|---|---|
| `account.create` | `{system_user}` | `{system_user, uid, gid, home, php_version, pool_socket, state: "active"}` |
| `account.suspend` | `{system_user}` | `{system_user, state: "suspended"}` |
| `account.unsuspend` | `{system_user}` | `{system_user, state: "active"}` |
| `account.delete` | `{system_user}` | `{system_user, state: "deleted"}` |

`system_user` is `lp` and 8 characters of `[a-z2-7]`. The target names the server and the account: `{"server_id": "…", "account_id": "<ULID>"}`. The panel needs `accounts.manage` to ask for them, and asks only from an account's screen, never a server's.

There is no `exec`, `shell`, `file.read`, or any operation that takes a command, a path outside a validated scope, or an environment.

### 6.2.1 Privileged operations: the `lpa-exec` socket (built in M6a)

The agent never runs an account operation itself ([ADR-0009](adr/0009-lpa-privilege-split.md)). After its own checks (§6.1), it hands the **signed operation, as the panel sent it,** to `lpa-exec` over `/run/lpa/exec.sock` (`0660 root:lpa`, systemd socket activation):

```json
{"v": 1, "operation": {"operation": "<base64url bytes>", "kid": "…", "signature": "…"}}
```

One request per connection, at most 256 KiB, read within 10 s. `lpa-exec` answers `{"status": "succeeded", "result": {…}}` or `{"status": "failed", "error_code": "…", "message": "…"}`. It trusts nothing from the agent:

1. The peer must be the `lpa` uid (`SO_PEERCRED`). Anyone else gets no answer at all, and is logged.
2. It verifies the panel's signature itself, with the key in `/etc/lpa/enrollment.json`, then decodes strictly and applies §6.1's checks (addressed to this agent, within `not_after`, in **its** registry, target fits the scope, idempotency key present).
3. A succeeded idempotency key is remembered for 7 days (`/var/lib/lpa-exec/journal`), and a repeat gets the stored result without running again. So a compromised agent can't replay an old `account.create` to undo a later delete.
4. It runs one operation at a time, to the end, even if the agent hangs up. A cancel does not stop it; its real result is reported.

If the agent loses `lpa-exec`'s answer after sending the request, it reports `needs_attention / adapter_unavailable`: the server may have changed. Retrying is safe, because every account operation converges.

The two sides are kept in step by a file: the agent's tests write `internal/ops/testdata/catalogue.json` (every definition plus a real result of each operation), and the panel's `OperationCatalogueTest` checks its catalogue against a copy of it, including that each real result passes the PHP result schema.

### 6.3 Lifecycle on the panel (built in M4)

States, per [ADR-0006](adr/0006-operations-separate-from-queue.md): `queued → claimed → running → succeeded | failed | needs_attention`, plus `cancelled` and `expired`. "Claimed" is an agent holding the lease; the first lease extension makes it "running".

- **Claim.** Oldest queued first, for the claiming agent's server only, with `not_after` in the future. Each is taken with a guarded `UPDATE` (on status and attempt), so a concurrent claim cannot take it twice. `attempt` goes up by one per delivery, so the agent's journal never takes a redelivery for a duplicate. The envelope is built and signed before the claim, so nothing is claimed that cannot be sent; with no operation key the claim answers `503`.
- **Lease.** `lease_seconds` = the operation's timeout + 30 s (30 to 3600). The agent extends it every third of that. A lease call for an attempt that no longer counts (finished, cancelled, or superseded after a lapse) is answered `cancel_requested: true`.
- **Result.** The first result for an attempt up to the current one wins, even an earlier attempt's after a lapse (that work did happen). A resent copy of the result already taken is answered `{accepted:true}` and changes nothing. Anything else is `409 result_conflict`, which the agent drops. A `succeeded` result that fails the result schema is stored as `failed / invalid_result`, keeps nothing of the result, and is audited (`operation.invalid_result`).
- **Sweeper** (`operations:sweep`, every minute): queued past `not_after` → `expired`. A lapsed lease → back to `queued` if the operation is idempotent with attempts left; else `failed / lease_expired` if it is read-only, `needs_attention / lease_expired` if it may have changed the server; `cancelled` if a cancel had been asked for.
- **Cancel.** A queued operation is cancelled at once. A claimed or running one gets `cancel_requested`, which the agent reads at its next lease extension; it stops and reports `failed / cancelled`, stored as `cancelled`. If it finished first, its real result is kept.
- **Revocation** cancels every live operation of that server in the same transaction (`agent_revoked`).
- **Refused at creation**, not queued to fail later: an operation the panel does not define, a person without its capability, a payload that does not fit, a server that is not paired, revoked or online, and an agent whose heartbeat lacks protocol 1 or the `op`/`op_version`. An identical read-only request still live is joined instead of queued twice.

## 7. Result (agent → panel)

```json
{
  "operation_id": "…",
  "attempt": 1,
  "status": "succeeded | failed | needs_attention",
  "error_code": null,
  "message": "safe, human-readable, ≤ 500 chars",
  "result": { },
  "started_at": 1793000001,
  "finished_at": 1793000002,
  "agent_version": "0.1.0",
  "truncated": false
}
```

- `result` must validate against the operation's `result_schema`, or the panel stores the operation as `failed` / `invalid_result`.
- No raw stdout or stderr is ever included. Adapters map process output to error codes. Short, redacted diagnostics go in `message` only when the operation definition allows it.
- The agent stores `(idempotency_key → result)` in its local journal (`/var/lib/lpa/journal/`) for 7 days. When a delivered operation's key is already in the journal, the agent returns the stored result without acting again.

## 9. Versioning

- `protocols` in the heartbeat lists every protocol version the agent speaks. The panel uses the highest version both sides share.
- An operation is offered only if the agent's latest capability document lists that `op` and `op_version`. Otherwise the panel refuses it at creation (`unsupported_op_version`) instead of queueing it.
- Golden vectors in both repositories pin the format: the signing string, an operation signature and a result. Each side's tests verify the other side's vectors.
